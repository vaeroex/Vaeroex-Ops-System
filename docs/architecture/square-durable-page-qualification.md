# Dormant Square trusted authority and durable-page qualification

Baseline: PR #350 merge `fd1aee715504d78efe21d844874e0e054ebaa7f4`. This milestone adds a checked private database implementation of its authority and atomic page repository interfaces. It does not activate Square or verify real Square OAuth identities.

## Agreed compatible additions

The existing `commit_provider_external_source_record_version_v1` is deliberately QBO-only and commits one source. Composing it with a checkpoint update is not atomic multi-source persistence. Generic runtime cursors remain limited to 1,024 characters; Square continues to support its existing 4,096-character private cursor contract. Neither existing RPCs nor these contracts are widened.

Dedicated private Square tables retain connection/generation evidence, explicit location/entity mappings, tasks, scans, immutable pending source versions, resource pointers and page receipts. The application continues to use `SquareIngestionAuthority` and `SquarePageRepository`. New factories require an explicit checked database client and fixed task/lease-owner context; no environment, credential, transport or runtime defaults are introduced.

## Authority and closed activation gates

The runtime principal is a real least-privileged database login with only the dedicated runtime execution capability. Each enrolled task binds its actual `session_user`, lease-owner fingerprint, workspace, Business Entity, stable connection, seller, environment, generation, projection stream, operation and exact query. A caller-supplied identifier or shape-valid Merchant/Location response cannot create verification or mapping authority.

The migration grants no runtime or qualification role to customers, `service_role`, QBO authorities or an application login. Qualification enrollment requires a separately installed disposable-database marker and dedicated qualification administrator. Synthetic identity evidence is explicitly labeled as such; it is not represented as completed OAuth verification. No production enrollment/registration or general ID-to-verification helper is provided.

A stable connection has a current-generation fence; generation-specific verification, mapping and retention evidence is immutable. Revocation invalidates future reads and commits without rewriting or deleting prior source observations or their authority evidence. New generation enrollment cannot revive an old task. Default-location use requires explicit discovery evidence and an explicit mapping; omitted defaults do not select another location.

Machine-role authorization follows the repository's existing `session_user` membership pattern, rather than relying on mutable session GUCs or user-controlled JWT metadata. Every checked entrypoint revalidates database authority; application preflight is not the transaction's authorization decision. Private tables have no direct runtime/customer grants and use RLS as defense in depth. Function execution defaults are revoked and search paths are fixed.

## Transaction ordering and recovery contract

All checked operations lock the connection authority row first, then the immutable task, per-connection capacity row and mutable scan, followed by resource rows in stable order. Revocation/generation changes take an incompatible lock on that same connection row. The capacity lock serializes bounded writes for one connection without changing the descriptor's read-concurrency declaration. Eligibility and expiry use the database clock after waiting for locks, not a client timestamp or an early transaction timestamp. Final publication rechecks the input cursor as well as task, retention, lease, next cursor and disposable gate after resource waits.

A valid page transaction appends all minimized pending versions and provenance, allocates immutable ordinals/prior pointers, deduplicates content, records the page receipt, accumulates completeness limitations, stores the private next cursor and advances the checkpoint together. A failure before commit rolls back every effect. A lost acknowledgement after commit is uncertain delivery, resolved by the durable receipt/checkpoint; it is not claimed rollback or distributed exactly-once execution.

Resource identity remains separate from content-version identity and projection scope. Duplicate versions preserve the first observation. Observed and provider-current pointers are separate: older, unordered and conflicting changes remain historical without silently replacing the current candidate. Only explicit supported Catalog tombstones represent deletion. Missing records never imply deletion. Exact provider version and timestamp text must retain sub-microsecond distinctions; PostgreSQL timestamp rounding is not used as the ordering comparator.

All stored generic envelopes stay `pending` / `untrusted_external_input`; no canonical economic contribution, reconciliation, stock calculation or complete-history inference is added. The final generic fingerprint is derived after ordinal-dependent change kind is known, not copied from an incorrectly preallocated first-version envelope.

## Cursor privacy, retention and bounds

Cursor text is stored only in the private checked boundary, following existing private checkpoint conventions: no customer-visible status, unrestricted view, diagnostic or log includes it. Checked worker reads bind the cursor to connection, environment, generation, stream, query, task and lease ownership. This access-control design is not a new application-layer encryption or KMS claim.

Retention approval and versioned policy are explicit prerequisites. Existing workspace `historyHorizonDays` / `retentionPolicyVersion` conventions remain relevant, but this milestone does not invent Square production retention durations, purge authority or long-lived audit retention decisions. Unconfigured or expired approval closes access/commit gates. Clearly synthetic finite values may be enrolled in disposable tests. No purge job runs and revocation does not authorize deletion of immutable history.

The inner application command preserves PR #350's 66,000-container, 7.2-million-value, 64 MiB serialized-byte, depth-64, 3,000-source and 4,096-character limits. Descriptor-first inspection occurs before schemas, hashing or RPC serialization; repeated shared objects count per expanded occurrence. The existing mapped-page derivation (largest supported conservative page: 65,004 containers) is reused, not replaced by a larger empirical fixture cap. The RPC adds only fixed task/owner routing fields; SQL must validate the same inner command before fingerprint traversal. Database transaction and retained-state limits are documented with the implemented migration and qualification evidence below.

The SQL guard checks the root's physical JSONB size (128 MiB) before traversal, then counts compact serialized bytes, UTF-16 string lengths, every value/container and depth. It descends only containers, rejects excessive immediate cardinality/budget before descending, and charges scalar children in a shallow aggregate. A depth-first path stack retains bounded metadata instead of a recursive result spool; at most 66,000 container visits, 7.2 million immediate values and depth 64 are permitted before any source fingerprint. JSONB has already expanded any shared application references, so aliases receive no discount.

The visitor is a single **nonrecursive** depth-first loop, `STABLE` with function-local `plan_cache_mode = force_generic_plan`. Expanded frame/index arrays retain only child-key names and traversal positions, never ancestor payloads. The local planning setting overrides even a caller's `force_custom_plan` before the body runs and avoids substituting copied root constants into plans. Iteration also removes per-container recursive PL/pgSQL calls and reentrant expression/SPI execution. The argument, parameter-substitution, function-GUC and plan-cache behavior was checked against PostgreSQL source; elapsed-time measurements are corroboration, not the allocation proof.

For short flat identifier arrays, a bounded shortcut avoids millions of per-scalar SQL operations. Container, value, depth and cardinality checks still run first. The extracted, detoasted JSONB must fit 32 KiB, and a strict immediate-child JSONPath type check must prove every element is a string **before** whole-array serialization. This ordering prevents compact binary Numeric exponents from expanding into large text. Only then does a C-collated anchored pattern recognize unescaped ASCII strings of at most 255 characters. Each rendered JSON text is bounded to 192 KiB; serialization and regex evaluation use a fixed number of bounded buffers, not a single-copy or peak-heap guarantee. Compact bytes equal JSONB text bytes minus exactly one formatting space per comma. All occurrences are charged, no child containers are skipped, and every other value uses the unchanged general checks. The 32 KiB/255-character thresholds select an optimization only; they are not new acceptance limits.

Square hashing uses a separate **nonrecursive canonical token emitter**, not the unchanged generic/QBO recursive serializer. It retains only child-key/ordinal and index arrays while descending root-relative paths; each shallow query finishes and releases child JSONB/scalar batches before descent. Disjoint scalar runs are emitted immediately. Numeric order paths restore the existing C-key ordering and array order in one final ordered aggregation. For `C` containers there are at most `5*C+1` token rows; token text sums to one canonical representation, rather than a representation per ancestor. Sorting can spill, and final aggregation/UTF-8 conversion has a fixed number of bounded buffers; this is not a claim of zero allocation or a single physical copy. Internal fingerprint wrappers add at most 64 containers, 1,000 values and 16 KiB to the already-validated subtree without increasing its depth beyond the original command's 64. Public accepted-command limits are unchanged. Generic source fingerprint bytes remain exact.

Dedicated retained state is capped per stable connection at **32 scans, 10,000 resources, 10,000 immutable versions, 3,200 receipts, 64 MiB logical compact-JSON bytes and 500,000 containers**. Transactional AFTER-row accounting includes both pending and final generic projections, cursor/lease copies and row metadata; skipped `ON CONFLICT` inserts do not charge capacity. A staged source row may temporarily contain two copies of the bounded command projection plus fixed wrappers; its accounting budget is explicitly finite, and complete retained state must still fit the smaller cap. Capacity exhaustion rolls back all staged page/source/receipt/counter changes and can publish only a blocked, incomplete scan with unchanged checkpoint. No receipt or immutable version is evicted to admit new work. These are qualification limits, not approved production retention durations or a purge policy. Trusted enrollment metadata is administrator-controlled rather than an untrusted streaming sink.

## Migration and qualification workflow

The two additive files were created with the pinned Supabase CLI. Development and tests may mutate only an independently verified disposable local database. The harness must reject remote URLs, linked-project configuration and inherited cloud/database credentials. Administrative setup creates the owned disposable database and dedicated test logins; actual runtime enrollment and application writes use designed checked entrypoints, not service-role or direct application DML shortcuts.

Qualification covers complete installation and upgrade from the baseline, migration transaction failure, independent-session concurrency, lease expiry/CAS, revoke-before/after-commit ordering, connection/process interruption and lost acknowledgements. Native PostgreSQL platform prerequisites and actual Supabase CI evidence must be distinguished. No test may claim host/power-loss durability merely from transaction rollback or client interruption.

Run `node scripts/run-square-durable-page-qualification.js` with `SQUARE_QUALIFICATION_PG_BIN` pointing to an installed PostgreSQL 17+ `bin` directory. The local installation must provide the extensions required by the unchanged migration chain (`pgcrypto`, `dblink`, `vector`). The harness creates and verifies its own cluster, private Unix socket and nonce-named databases; it accepts no user-supplied database URL. Local qualification used PostgreSQL 17.11 and 17.6 with pgvector 0.8.6 built from official sources in temporary directories, not system services. The final corrected suite ran on 17.6, matching the CI image's PostgreSQL release; these are disposable qualification runtimes, not production version recommendations.

Native source pins: PostgreSQL 17.11 archive SHA-256 `dd27f2b3c59e73ed14aa3324901242bf69a032a6347805f274e6260322d42979`; PostgreSQL 17.6 archive SHA-256 `e0630a3600aea27511715563259ec2111cd5f4353a4b040e0be827f94cd7a8b0`; pgvector 0.8.6 commit `8ee86c96f0fd72390f890aa8a336fda6d3ab4c6c`. Optional `--local-advisors`, with `SUPABASE_CLI_PATH` selecting the pinned CLI, runs read-only advisors on the already-verified disposable target with no linked fallback.

CI uses `--supabase-local` after its existing isolated Supabase database startup. It verifies the local Docker context, exact project container and matching loopback port before creating separate nonce databases. Those databases use a minimal Auth/Storage SQL prerequisite scaffold and all repository migrations unchanged; this does **not** implement Supabase Auth/Storage services. The existing `security-database` gate separately installs and tests the full application migration chain on the actual Supabase image, then runs the unchanged QBO fixture-rich upgrade checks. No linked/hosted target is accepted by the Square harness.

The harness removes only its explicitly tracked disposable databases/logins and stops only its owned native cluster. Native cluster files remain recoverable in its owned temporary location; no workspace or immutable application history is deleted. Test setup may install marker rows, create synthetic tenant fixtures, expire local lease/cursor fixtures, or add a temporary failure trigger as the disposable owner. Application writes and enrollment themselves always run through the actual dedicated runtime/qualification logins and checked functions.

Safe rollback is operational disablement and revocation of newly granted Square execution capability; retain immutable tables/history. Forward recovery applies a reviewed additive correction. Do not run destructive down migrations or remove an installed migration-history entry. The existing QBO fixture-rich upgrade chain remains pinned; only the exact two dormant Square migrations are allowed after it, and QBO tests still execute against the upgraded database.

Legacy parser scope assertions share an exact five-path exception for these two migrations and three qualification fixtures. Neighboring files, other migrations and activation/runtime paths still reject. Parser purity, authority, registry and fingerprint assertions are unchanged; no whole-directory exemption is introduced.

## Evidence and remaining prerequisites

Completed local evidence:

- Real PostgreSQL qualification: **569 assertions / 226 scenarios** on 17.6, including the final deep-payload, iterative/flat-array and restricted-diagnostic witnesses. Clean installation and baseline upgrade run the entire unchanged migration chain; injected failure before each additive migration's COMMIT leaves no partial new schema. Forward retry succeeds. Preexisting create/correction/tombstone rows, immutable links, fingerprint bytes, current pointer and mutation-denial protection survive.
- All 25 current operation/projection paths run the real PR #350 decoder/parser/mapper through actual least-privileged LOGIN authority and page RPCs. Database-materialized generic source fingerprints match the established TypeScript implementation byte-for-byte. All eight pageable cases preserve a private 4,096-character cursor across a fresh session; 4,097 rejects without checkpoint advancement.
- Actual independent sessions establish both commit/revocation lock orders, expiry after waits, competing lease ownership and stale-worker denial. A process is killed on either side of COMMIT. A temporary owner-installed failure after the second source INSERT proves whole-page rollback, then successful retry. Lost acknowledgements resolve through receipts; conflicting page reuse rejects. No host/power-loss, distributed exactly-once or real provider qualification is claimed.
- Recomputed-hash foreign-scope attempts, direct-table access denial, privacy canaries, cumulative unsupported/returns-unknown limitations, exact nanosecond revision ordering, late/equal observations, duplicate-counter invariance, scan 32/33 and transactional retained-capacity exhaustion are covered. Near-byte-cap testing uses an explicit owner-only counter fixture, not a claim to have filled every byte of historical storage.
- SQL and application guards cover 66,000/66,001 expanded containers, scalar depth, UTF-16 length and hostile input. The supported Catalog witness genuinely uses **20,000 raw values, 3,000 roots and 1,000 explicit authorized locations** (three million repeated scope values). The final native run committed in **11,134 ms**, below the unchanged 30-second lease and 64 MiB capacity. Its isolated whole-command guard took 970 ms, returned the exact logical budget, and made one visitor call. Timing is an observation, not the structural bound or a production latency SLA.
- Fresh-session depth-60 JSON with **8,192,000 scalar characters** passes guard plus canonical fingerprint parity in 7,543 ms under default `auto` planning and 8,243 ms under caller `force_custom_plan`. Local build activity overlapped, so these are completion observations, not a comparative planning benchmark. The function-local generic setting is asserted from installed metadata. This workload corroborates the reviewed allocation structure; elapsed time is not a peak-heap measurement or a substitute for the structural proof.
- Iterative accounting covers empty/scalar roots, mixed sibling/ancestor popping, nonempty entry paths and exact exhausted budgets. The fast-path selector is checked at 32 KiB minus one, exactly 32 KiB and plus one; accepted/fallback ASCII lengths, escapes, controls, Unicode, mixed containers, huge Numeric exponents and later foreign authority are covered. Optimization thresholds never replace the original acceptance limits.
- The corrected maximum Catalog page also committed on the actual Supabase CI image in 20,649 ms, retaining 27,800,362 logical bytes. That run subsequently exposed privileged session-configuration/statistics-reset assumptions in a diagnostic, not a failed page commit. The diagnostic now uses a separate owned nonsuperuser login with only the two pure JSON helpers, owner-configured tracking and an observed counter delta. Regressions prove it cannot change privileged tracking, reset statistics, read source tables, join runtime/administrator authority or call the page-commit RPC. No runtime grant, shared owner setting, page limit or lease changed. Full exact-head CI remains the delivery gate.
- All 33 application integration regression suites, TypeScript, ESLint (the unchanged 59-warning baseline), security checks, both QBO runtime builds and the application production build pass locally. The required CI additionally exercises its pinned Go/WASM/Terraform tooling and real Supabase installation/upgrade jobs.
- Local Supabase advisors: 27 preexisting public-policy warnings (`auth_rls_initplan` / `multiple_permissive_policies`), no Square finding. No unrelated policy edits were made. Required exact-head `verify` / `security-database` and automatic Vercel Preview checks are registered and must pass before delivery; the delivery PR is the authoritative record of those results. Preview is an application build, not database/provider activation.

Integrated self-review corrected the Inventory snapshot record-type mismatch, SQL traversal/depth/UTF-16 parity, source fingerprint materialization, fixed RPC-error redaction and complete retained-state accounting. Separate independent review identified and verified corrections for input-cursor expiry after resource waits, recursive custom-plan root copies and recursive canonical child-subtree copies.
