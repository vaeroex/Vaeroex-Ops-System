## CL-04 / VXA-022: confirmed file-analysis publication

The application calls one authenticated-only `SECURITY INVOKER` RPC, `publish_confirmed_file_memory_v1`, instead of separately inserting chunks, archiving a capped list of prior IDs, and updating a stale file metadata snapshot. The RPC uses a fixed empty search path and ordinary caller RLS/subscription authority. It explicitly verifies the authenticated actor/operator, locks the live same-workspace source, rejects hidden/archived/processing files, checks the current analysis-run pointer, and locks and validates that completed run's file lineage and evidence classification. A stale run cannot publish after waiting behind a newer generation.

All chunk inserts, unbounded server-side retirement of prior active file-analysis chunks, locked-current metadata merge, counters, and completion job commit together. Insert keys include file, run, ordinal and excerpt; different runs with identical text get distinct citation IDs. Previous rows are archived, never deleted or relabeled to the new run. A receipt fingerprint records the confirmed content/summary; the same request after an ambiguous acknowledgement returns the same chunk IDs without a second completion job. Changed same-run content fails. Deliberately withdrawn history is not automatically revived. Publication time is captured after authority/freshness locks, not before waiting.

The actual app still performs its existing tool permission/confirmation and source grounding preflights; the RPC does not infer consent from model output. The final helper returns an unavailable result when publication cannot be verified and does not perform a second stale metadata overwrite.

Native focused proof: **34/34**, `/tmp/vaeroex-memory-publication-results.json`. This includes 1,205 prior chunks retired without changing their IDs/provenance; transaction rollback on injected final-job failure; acknowledgement-loss replay; 16 independent sessions yielding exactly one publication/15 replays; revoked role, foreign tenant/actor, withdrawn source, expired subscription, stale generation and in-progress processing denial; changed same-run content; repeatable-read serialization failure; preservation of unrelated metadata. Anonymous and generic service execution are denied.

Scope boundary: this is the cooperating confirmed file-analysis publication path. Existing contributor table-write privileges are not made generally immutable by this migration. Embeddings are represented as `real[]` in this reduced native fixture; root/data's real Supabase/pgvector replay is the authority for actual vector schema compatibility. This does not establish throughput or active-user capacity.

## CL-05 / VXA-021: durable acceptance and truthful import recovery

The new private attempt receipt records workspace/source/import/preparation, approving actor, selected row IDs, reviewed mapping, prior completion timestamp, and durable state. It is inaccessible to ordinary authenticated and generic service clients. Admission checks live authenticated operator membership and entitlement, locks membership and source, verifies selected staged rows, and admits at most one unresolved attempt per source. Sixteen independent clients produce one admitted writer. An unknown admission response never authorizes a second writer. No timeout or automatic lease reset converts an uncertain attempt into retry permission.

Both workbook and legacy actions now perform only validation before admission; all row diagnostics, labels, skipped status, processing state, settings and business writes follow the durable claim. Denied/ambiguous claims leave existing row/import/file/business state untouched. The staged source mapping stays immutable while the receipt retains the approved mapping. Invalid validation returns the error without modifying a possibly concurrent winner. The database trigger freezes unresolved staging data, source identity, and preparation generation, checking both OLD and NEW same-tenant source IDs in deterministic order so reparenting cannot escape the freeze. Public recovery_status is derived from the private receipt, not client-supplied state.

The application verifies both errors and affected-row counts at completion boundaries. Reconciliation inventories actually persisted KPI/metric rows, active worksheet chunks and approved row outcomes. Completion requires matching import/file timestamps and all approved rows in an accepted outcome; a previous generation's file marker cannot confirm a newer generation using the same import ID. If final acknowledgement was lost after all completion markers persisted, readback can report recovered completion without resubmitting anything. Otherwise it records/retains a running or reconciliation_required hold and preserves accepted rows. Recovery remains readable after billing expiry and never grants a fresh write admission.

The UI exposes “Check saved results” for held work and hides automatic reprepare/reimport. The response reports persisted counts and explicitly says a still-running/partial attempt cannot be retried automatically. A genuine partial import is intentionally held for a trusted operator to verify that the worker stopped and reconcile saved inventory; there is no automatic reset, resume or deletion API. Workbook publication returning zero memory chunks cannot write successful completion markers or claim Business Memory success. Nonzero text-only evidence remains acceptable when optional embeddings are unavailable.

## Worksheet historical provenance correction and remaining boundary

The prior worksheet helper hashed only file/worksheet/text, so later separately approved preparations with the same text upserted one chunk and replaced its import provenance. The caller now supplies the durable attempt ID; hashes and source metadata include it. Same-attempt content keeps a stable identity, while a new approved attempt receives distinct IDs and retains older citation/excerpt/import metadata. The actual indexer adapter tests this, and restoring only the former hash in memory causes the test to fail with one shared row instead of two. See `/tmp/vaeroex-worksheet-generation-before.log` and control script. Parser/indexer regression suite now **26/26** in `/tmp/vaeroex-memory-app-regression.json`.

A subsequent focused review verified that the former 320-row pre-retirement implementation could mix old and held-attempt chunks in retrieval after an applied-write/lost-acknowledgement response. That was classified as a finite release blocker, not a capacity-only concern. Proof is preserved at `/tmp/vaeroex-worksheet-held-retrieval-proof.{cjs,json}`. The approved correction removes pre-publication retirement entirely: worksheet generations append with distinct IDs, and only the latest completed private receipt selects the current worksheet generation. Previous evidence remains intact while a newer attempt is held. Existing untagged legacy worksheet chunks remain eligible only until the first durable publication completes. Older completed or pending generations stay physically readable history but are excluded from current retrieval.

The new forward migration is `20261005070311_worksheet_import_publication_heads.sql`, SHA256 `56c6a11c3317bee9f1f75269b94163a399539bae0272ed5a2a4451ec0eb283ca`. The vector-match RPC retains its original signature, INVOKER mode and other filters, adding the same completed-head condition before rank/limit. Shared application retrieval reads heads in200-ID batches, rejects malformed/missing/duplicate/unrequested responses rather than enabling legacy fallback, and retains existing file/run/note lifecycle checks.

Chunk and index-status acknowledgements now require exact returned row counts. Indexed count refers to this generation, not accumulated historical rows. The Sources detail and list identify held imports rather than claiming availability for an unpublished generation. A separate status-only loader checks listed fileIDs in200-ID batches, verifies exact response counts, and reports unavailable status instead of Learned when a query fails or truncates. This status source is independent of the300-row historical import display; it does not remove history. The detail panel passes that status source separately, and the review component selects the actual held same-file receipt for its hidden request ID and Check saved results control. When status cannot be verified, it renders feedback without approval/reprepare forms.
