## Scope, compatibility and release gates

- These tests emulate auth.uid()/auth.role()/auth.jwt() from request GUCs. Supabase/PostgREST must set those from verified JWTs; direct database credentials able to SET arbitrary claims are a different trust boundary. Source scan found no exposed routine setting request.jwt claims. No real isolated Auth accounts/HTTP unauthorized requests, Storage HTTP, full provider RPC workflow, or full deployed schema replay were performed. Focused provider tables emulate only the columns the new entitlement trigger reads. Full matched-schema integration qualification remains a release gate; do not claim every function/workflow is proved compatible.
- Static inventory recognizes 92 public table declarations, 77 with UUID workspace_id and 72 proposed public guard candidates. This is a syntax scan with documented overload/dynamic-DDL limitations, not a live catalog or complete schema proof. The actual migration selects existing RLS tables from pg_class at application time. Prior preserved production metadata records no public tables without RLS, but no production migration was applied. Reconcile actual applied trigger/policy counts on an isolated matching schema before release.
- **Mandatory release prerequisite:** an authorized operator must reconcile the existing `VAEROEX_ADMIN_EMAILS` configuration to verified `auth.users.id` identities and populate the private subscription exemption table before enabling enforcement in production. Do not derive IDs from a client-supplied email or metadata field, and do not include actual identities in the public audit. The private allowlist must be updated whenever platform-admin authority is revoked; otherwise its trusted exemption remains active. The migration deliberately ships empty. An unconfigured regular admin session obeys ordinary billing rules. Server-role bootstrap/billing recovery remains available.
- Service-client analysis parity is implemented through `public.create_trusted_analysis_run_v1`, executable only by service_role and guarded by the original service JWT role. The authenticated caller cannot invoke it or forge its private transaction-local authorization. The server supplies an actor obtained by existing `auth.getUser()` and consent/subscription preflight; the RPC independently requires active workspace membership with an existing valid role and billing entitlement or the private admin exemption. Exact workflow allowlist: `business_health_explanation_v1`, `intelligence_briefing_v1`, `finding_explanation_v1`. It fixes status to processing, generates ID/time, initializes empty output, and binds created_by to the checked actor. The quota trigger accepts an exemption only from the RPC's matching private run/workspace/actor/transaction claim, then the RPC removes that claim. Direct service inserts cannot borrow an exemption merely from created_by or a JWT subject. Ordinary actors remain subject to existing billing and persisted quota. Both generation reuse paths retain SQLSTATE 23505 even at full capacity. The three caller edits are `lib/ai/business-health-explanation/generation-claim.ts`, `lib/ai/intelligence-briefing/generation-claim.ts`, and `app/app/finding-explanation/actions.ts`. File uploads/file analysis use authenticated clients and need no service-actor bypass.
- **Bounded RPC input and compatibility:** input must be a JSON object with PostgreSQL `pg_column_size(input_json) <= 262144` (256 KiB). Native tests accept exactly 262144 bytes and reject 262145 with SQLSTATE 22023. Actual caller initializer fixtures with generous 1024-byte scalar strings and MAX_SAFE_INTEGER counts measured 7546 bytes for Health, 11704 for Briefing, and 5454 for Finding; all three were accepted by the actual RPC. These measurements establish representative current-shaped compatibility, not a formal maximum over every future product input. The initializer currently carries references, version fields and counts, not source document bodies. Health/Briefing return failed_closed for any non-23505 RPC failure; Finding returns its generic safe failure before provider generation. Oversized/missing-RPC requests therefore do not proceed to model generation through these paths. Qualify any future larger shape against this cap before release; do not silently raise or remove it.
- **RPC release order:** apply and qualify both migrations, reconcile the trusted exemption allowlist, then release the three updated service callers. Missing RPC/schema intentionally fails closed. The new table remains private and unseeded in source. No global service-role quota bypass or change to provider billing accounting was introduced.
- Both NOT VALID FKs require historical mismatch review before validation; migration retains every row. Approval to delete or rewrite historical records has not been assumed.
- Persisted slots do **not** guarantee that a provider call which happens before ai_agent_runs insertion is reserved. Other quota categories (workspaces/users/forms/checklists), provider spend/token budgets, overlapping provider invocations, and historical hard-delete billing behavior remain outside this atomic slot fix. The server-run timestamp guard does not rewrite old records. No claim of strict pre-provider quota is made.
- The audit writer requires the existing server service-role credential and applied provenance column before the updated gateway operates; missing setup deliberately blocks tool actions. Do not deploy code before migration/schema qualification. Legacy blocked events no longer contribute to lockout counts because their issuer cannot be retrospectively authenticated.

Reverting security restrictions reopens verified defects; do not restore client audit INSERT or remove tenant FKs without equivalent controls. Historical data migration is a separate approval.
