## Preflight and execution checklist for a future approved release

1. **Freeze the exact artifact.** Record stack heads, final application commit, lockfile and `patches/next@15.5.24.patch` hashes, qualified runtime regressions and final CI. Keep the original deployment holds until a separate explicit release authorization changes them. Record workers and scheduler versions/configuration with the application. Capture only configuration names and nonsecret fingerprints in public evidence.
2. **Reconcile the destination.** Under separately authorized operator access, compare actual deployment, provider enablement, Auth configuration and migration ledger with the chosen production shape. Any unrecognized applied migration or incompatible running worker stops this sequence for reconciliation. Check required owner access, current recoverable backup/restore evidence, free storage and the migration lock/statement timeout policy. The isolated millisecond timings do not predict production-volume locks or index build time.
3. **Approve identities privately.** Normalize the actual `VAEROEX_ADMIN_EMAILS` entries exactly as code does (trim/lowercase; comma, semicolon or newline separators). Resolve each to one current `auth.users.id`; verify email/account status, owner approval and intended membership. Reject ambiguous, missing, deleted or banned candidates. Record expected ordinary-role denials and a revocation owner. The public audit stores roster count and approval reference only, not actual identities or credentials.
4. **Inventory before writes stop.** Capture scoped counts/IDs/hashes for historical parent mismatches, future-dated asset checks, unresolved imports, active publication/import heads and accepted integration work in a protected operator artifact. Inventory old in-flight imports separately: the new receipt migration deliberately does not invent historical receipts. Quiesce or explicitly classify them before admitting the new import action. Preserve original queue eligibility/lease/generation and any unknown acknowledgements.
5. **Enter the approved write window.** Stop the named admissions and drain/inventory workers. Keep recovery controls reachable where their compatible path is verified. Do not shorten a lease or ignore a stale-worker fence to accelerate the window. In particular, pre-migration Sheets leases retain their original 480-second deadlines; drain them under the hold and qualify new 270-second leases separately. Never rewrite old lease timestamps to claim a 300-second result. If accepted work cannot reach a known outcome, retain a hold and record it; do not call it drained.
6. **Apply the exact ordered tail using the approved ledger-aware migrator.** Each file has its own BEGIN/COMMIT. There is no cross-file atomic transaction covering the thirteen-file rollout. Stop on the first error and retain the write window. Record each confirmed committed migration, hash and ledger entry. The first migration creates an empty exemption table and entitlement enforcement in one transaction; exemptions cannot be seeded before that table exists. Keep writes closed throughout the enforcement-to-configuration gap.
7. **Configure only the approved exemption UUID set as database owner.** API roles, including `service_role`, cannot read/write the private table or gain private-schema USAGE. Use parameterized, individually reviewed inserts; compare the result with the approved roster and investigate unexpected existing rows before changing them. Do not copy a synthetic fixture roster or grant table access to a service client for convenience. Configure before reopening affected writes.
8. **Install the matching application and workers under the same hold.** The new RPC callers must not precede their migrations; old workers/callers must not run concurrently where they can bypass receipt/publication contracts or write legacy audit semantics. Retain the React runtime patch and both regression tests. Do not change provider activation gates as part of this release.
9. **Verify with approved isolated/canary resources before reopening.** Check exact schema/ledger, private ACLs, exemption/member/role behavior, expiry and recovery paths, one-effect form and issue replay/conflict, held and completed import reconciliation, current-head publication, Sheets aggregate/per-workspace admission and stale-worker rejection, plus QBO recovery isolation and pooled role/transaction cleanup. Confirm new run receipts have original eligibility; historical null eligibility must remain distinguishable from measured queue delay. Use test-only workspaces and simulated/sandbox providers; no customer connection mutation or paid generation is implied by this document. At production release time, any mutation canary requires its own approved synthetic workspace and scope.
10. **Reopen in a controlled order.** Confirm read availability and canary writes first, then normal browser/API admission, then background admission at its qualified aggregate budget. Observe trusted audit delivery, authorization failures, quota errors, accepted/completed/failed inventories, queue age, duplicate/lost records and recovery. Reclose affected admissions if a stop condition trips. Keep any held imports held independently of whether other workflows reopen.

Do not use a generic `supabase db push` from this mixed canonical/production checkout as the release command. The chosen operator's migration mechanism and credential delivery are not available in this draft, and no production command has been run. Approving the final release ticket must include that exact destination-checked invocation and its migration manifest; use the existing ledger-aware release process, not an improvised manual history repair.

where conrelid in ('public.asset_checks'::regclass,'public.form_submissions'::regclass)
  and conname in ('asset_checks_workspace_asset_fkey',
                  'form_submissions_workspace_form_fkey') order by conname;

Owner-only exemption statement pattern, requiring a separately approved verified `$1` Auth UUID. It is a **future authorized mutation template**, not a migration seed or executable roster:

```sql
insert into private.platform_admin_subscription_exemptions(user_id)
select id from auth.users
where id=$1 and deleted_at is null and email_confirmed_at is not null
  and (banned_until is null or banned_until<=statement_timestamp())
on conflict(user_id) do nothing;

Revoking an exemption is an individually authorized owner operation on that exact UUID, coordinated with removal of the application-side email/admin permission. ## Held-import decision tree and customer-facing outcome

Use the existing authenticated **Check saved results** control or the same `reconcile_file_import_attempt_v1(workspace, file, import, false)` call as an active owner/admin/manager. | Observed state | Allowed next step | Outcome / preservation rule |
|---|---|---|
| `completed`, matching receipt and completed file/import/row finalization | Show the saved completion and original receipt; repeat reconciliation may return it. | No rows resubmitted; no new attempt, KPI, metric or chunk. Keep original IDs and citation provenance. |
| Worker acknowledgement lost, persisted finalization independently complete | Run scoped reconciliation; its existing predicate may mark that same receipt completed. | Treat completion as verified only after the predicate succeeds. A count that merely “looks right” is insufficient. |
| `running` and an identified worker still owns live execution | Observe/wait for that identified execution, then reconcile. The import receipt is durable acceptance, not an expiring lease. | Do not concurrently retry/reprepare the source or kill a worker solely to make status appear terminal. |

## Failure and coordinated recovery

| Failure point | Required response |
|---|---|
| DDL error before a file commits | Keep admissions closed. Confirm that transaction rolled back; compare catalog/ledger, not just process exit. Earlier committed files remain installed. Correct the cause and retry only a proven unapplied migration through the approved mechanism. The retained rehearsals demonstrate atomic rollback/retry of the first migration and of migration8 with the earlier seven committed files preserved. |
| Migration COMMIT acknowledgement lost | Treat state as unknown. Read actual ledger **and** expected catalog/functions/triggers, reconcile with the migrator's transaction semantics, then decide. Do not blindly rerun CREATE statements or mark a migration applied based only on its filename. |
| Exemption configuration incomplete/wrong | Keep affected writes closed; repair only the approved owner-managed roster and matching server configuration. Do not grant private access or disable entitlement enforcement. Retest ordinary, viewer, foreign and revoked cases. |
| Matching application fails to start or qualification fails | Keep new schema/safeguards installed and admissions closed. Restore a qualified compatible artifact or produce a small forward code/schema correction in isolation. Do not deploy the pre-audit application to a receipt-enforcing schema as a default rollback. |
| Partial import / unknown worker / changed publication head | Preserve receipt, source rows, generation and heads; reconcile and hold as above. No “mark complete,” reclaiming without a fence, or deleting inserted data to simulate rollback. |
| Suspected loss, duplicate accepted effects or tenant breach | Stop affected admissions immediately, preserve logs/inventory, notify the incident owner and prepare a scoped forward recovery. Snapshot/backup restoration or historical edits need separate authorization and an explicit accepted-write reconciliation plan. |

Compatible fallback must understand trusted `server_recorded` audit provenance, database-owned readiness, persisted quotas, service analysis admission, internal-form and issue request receipts, import claims/frozen preparations, completed worksheet heads, Sheets bounded claim/recovery contracts and provider-scoped QBO recovery. Old scheduler binaries must not resume an unbounded or provider-generic recovery path. Retain the runtime backports and their tests. Pure presentation changes can be reverted independently after verifying they do not restore the original pending/notice defects. No fallback is declared qualified solely because an older build starts.

The safe default is a temporary affected-write hold with reads/recovery available where verified, not removal of constraints or rollback of receipt history. Backups remain an emergency capability; restoring one can discard accepted work after its timestamp and is not a routine inverse migration.
