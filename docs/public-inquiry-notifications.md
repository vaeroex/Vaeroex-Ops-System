# Public inquiry staff notifications

Contact submissions save support_requests with notification_status=pending, then atomically claim pending→attempting before calling existing Resend transport. Only /contact submissions are notified; existing support redirect and billing email routing remain. All new public inquiry notifications go to hq@vaeroex.com through the server-side general contact constant. The single authorized synthetic notification must also go only to hq@vaeroex.com. Customer support and billing addresses/routing remain unchanged. Submitted email is validated by the existing form schema and used only as Reply-To. Submitted text is escaped and limited to a 1,200-character summary. Admin links require existing platform-admin authentication and filter the queue by email.

Reuse the existing server-side RESEND_API_KEY with send permission for verified vaeroex.com; no second API key or email provider is required. Like the existing welcome and agreement senders, RESEND_FROM_EMAIL overrides the established default Vaeroex <hq@vaeroex.com>. INQUIRY_ADMIN_ORIGIN is an optional HTTPS override. By default Preview uses its server-provided VERCEL_URL (and fails closed if unavailable), while Production uses the existing getAppUrl()/NEXT_PUBLIC_APP_URL configuration. Never use a customer-provided origin or sender. Apply both 20261116010000_public_inquiry_notification_status.sql and 20261116010100_public_inquiry_notification_write_guard.sql before deploying code. The guard preserves legacy anonymous inserts while preventing callers from forging notification metadata. Preview migration was applied only to isolated project zfpnhvcmuuvtswttmnjd; Production remains untouched.

Admin → Support Requests displays Staff email status/detail on each request. accepted means provider acceptance only. failed includes safe configuration/provider HTTP categories; unknown means reconcile provider logs before any resend. attempting may mean a crashed process or unknown provider outcome. pending means saved but unclaimed. Review these states on refresh. No automatic retry loop blindly resends uncertain outcomes; do not reset unknown/attempting without checking provider records. Resend idempotency keys add bounded provider-side protection, while the durable claim prevents repeated sends after that window. Separate customer resubmissions remain separate inquiries. This is not a complete webhook-driven delivery/bounce tracker.

Saved requests remain successful if email/audit fails. Missing tracking schema is a release blocker, not a reason to claim notification works. A failed claim leaves pending state and emits only request ID diagnostics. No raw provider response, API key or customer message is logged.
